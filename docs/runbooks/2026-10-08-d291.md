## A. Validate 0092 on a production copy (TEST project)

**A restore replaces the TEST project's `public` schema and its data with production's.** Whatever
the TEST project holds now is lost, and production's rows — merchant data, analyst emails — are then
in TEST. Data for `vault_entries` and `credential_deposits` is excluded from the dump. Proceed only
if that is acceptable for the TEST project.

> **Run 2026-10-08 against TEST (`wakpxbojiqgbjuxikqab`) and passed:** 18 rows / 4 refusals on both
> sides, both constraints validated, behaviour checks ok. **TEST now holds production rows** — see
> A3b; no local worker may point at TEST until it is reset.

### A0. Confirm the client tools run, and the server version

    pg_dump --version; pg_restore --version; psql --version

Worked: three lines, each `(PostgreSQL) 17.x`. An *"Application Control policy has blocked this
file"* error means stop (see above).

Then in the **production** dashboard, SQL Editor:

    show server_version;

Worked: a version **17.x or lower**. A client older than the server refuses to dump it.

### A1. Collect the two Session pooler hosts

Each project has its own pooler host. For each: dashboard → **Connect** → **Session pooler**. Note
the host and the user, which is `postgres.<ref>`; the port is `5432`. (The guard tests in
`scripts/live/guard.test.mjs` use `aws-1-us-east-2.pooler.supabase.com` for production and
`aws-1-us-east-1.pooler.supabase.com` for TEST; copy the dashboard's values, not these.)

    $ProdHost = '<production Session pooler host>'
    $TestHost = '<TEST Session pooler host>'

### A2. Dump production (read-only)

The dump goes to `%TEMP%`, outside the repository, so it can never be committed. `$Dump` is defined
once here and used by A4 and A8. The password is read without echo and never appears in the command
line or history.

    $Dump = "$env:TEMP\prod-public-2026-10-08.dump"
    $s = Read-Host 'Production database password' -AsSecureString
    $env:PGPASSWORD = [System.Net.NetworkCredential]::new('', $s).Password
    pg_dump --host=$ProdHost --port=5432 --username=postgres.rlevvxpttgzfxzysrigz --dbname=postgres `
      --schema=public --no-owner --format=custom `
      --exclude-table-data=public.vault_entries --exclude-table-data=public.credential_deposits `
      --file=$Dump
    Remove-Item Env:PGPASSWORD

Worked: no output, exit code 0 (`$LASTEXITCODE` is `0`), and `$Dump` exists with a non-trivial size
(`Get-Item $Dump`). The file holds production data: it is deleted in A8.

### A3. Count production's drafts

Worked: one row, `rows` and `refusals`. Write both down. On 2026-10-08, `refusals` was **4**.

### A3b. Confirm nothing polls TEST

### A4. Restore into TEST

    $s = Read-Host 'TEST database password' -AsSecureString
    $env:PGPASSWORD = [System.Net.NetworkCredential]::new('', $s).Password
    pg_restore --host=$TestHost --port=5432 --username=postgres.wakpxbojiqgbjuxikqab --dbname=postgres `
      --clean --if-exists --no-owner $Dump
    $LASTEXITCODE

Leave `$env:PGPASSWORD` set for A5–A7.

Expected: it finishes with `pg_restore: warning: errors ignored on restore: N` and a non-zero exit
code. **That alone is not failure.** Errors are expected for objects that reach outside `public`:
foreign keys into `auth.users` (production's analyst ids do not exist in TEST's auth), and objects
that storage policies depend on. What decides success is A5.

## B. Production, in this order

The order is the point. The web build reads `not_seen_cause` and the worker writes it, so **0092 is
live before either is deployed**. Netlify deploys on every push to `main` (DEPLOY.md §2: *"Push to
`main` deploys."*), so the push in B3 is itself the web deploy — it must not happen before B1.

### B1. Apply 0092 to production

Production dashboard, SQL Editor (DEPLOY.md §1.1): paste the whole of
`supabase/migrations/0092_draft_not_seen_cause.sql` and run it.

`supabase/manual/2026-10-08_validate_0092_shape.sql`.

Worked: `with_cause` = `0`, `rows` and `refusals` as in A3 (or higher, if drafts were written
since), and the same two constraint rows as A7, both `convalidated` = `t`.

An error saying `not_seen_cause` already exists means 0092 is already applied — check the shape file
and continue.

### B5. Deploy the worker

From the repository root, on `main`, with a clean tree (DEPLOY.md §3.5):

    git status --short
    $sha = git rev-parse --short HEAD
    fly deploy -a mintro-screener-worker --config apps\worker\fly.toml --dockerfile apps\worker\Dockerfile --build-arg GIT_SHA=$sha

Worked: `git status --short` prints nothing before the deploy; the build shows `toolchain ok`; the
deploy ends with the machine updated and healthy.

If the build instead fails looking for `apps/worker/apps/worker/Dockerfile` — the doubled path
DEPLOY.md §3.5 warns `--dockerfile` produces — re-run without `--dockerfile apps\worker\Dockerfile`;
`fly.toml` already names the Dockerfile. A failed build changes nothing on the running machine.

### B6. The startup line

    fly logs --app mintro-screener-worker

Worked, within a few seconds of boot:

    mintro worker · commit <$sha from B5> · rule sets peptides 3.11.0 (effective 2026-08-26), …
      ok    …preflight checks…
      ok    credentials    ready — key pair verified, public half derived from the private key

The commit must be B5's `$sha`. `commit unrecorded` means the build argument was not passed.
**The credentials line must read `ready`**: with it `not configured`, the worker cannot see the stored
login and the verification below reports *"No login is on file"* instead.

### C3. The records

Production dashboard, SQL Editor, read-only:

    select domain, platform from public.merchants where domain like '%thepeptide.com' order by domain;
