# Adult AI screener — design memo

Status: v0.3, ratified by Frank 2026-09-18.

Nothing here is built. Decisions D-284 to D-289 record the rulings this version rests on.

---

## 1. What this is, and the constraint it lives under

A second Mintro Screener vertical for merchants selling AI-generated adult content: companion chat,
image generation, and related products. Same infrastructure as the peptide screener; different rule
set, different intake, one new component (the probe library), and a stricter posture.

The posture comes from the Sponsor Agreement with IQWallet (25 Nov 2025):

- **1.4** — Sponsor is responsible for all referral and screening of Qualified Prospects.
- **1.5** — Sponsor's role is strictly limited to marketing, referral, onboarding, relationship
  management, support, and facilitation of information transfer. Sponsor does not perform
  underwriting, compliance adjudication, risk assessment, or fraud monitoring.
- **2.2** — IQWallet decides in its sole discretion whether to board.

So this vertical is D-001 (observations, not determinations) with a contractual citation and no
exceptions. It produces findings, cites the public source each finding relates to, and delivers
them to IQWallet before IQWallet decides. It does not score, grade, rank, recommend, or place.

### Hard constraints (this vertical)

| # | Constraint | Why |
|---|---|---|
| A1 | No verdict of any kind reaches a merchant, agent, or IQWallet. No score, pass/fail, risk tier, placement, or recommendation. The words "fail", "pass", "blocker", "clean", "compliant" do not appear in rendered copy. | 1.5 |
| A2 | Merchant-level exclusion happens only at intake, only by category or feature, never by judgment about a specific merchant. | 1.1 (marketing discretion) vs 1.5 (no risk assessment) |
| A3 | The tool never requests, generates, stores, or classifies a prohibited artifact. Probes are text-only, precursor-only, graded from response text. No image or video is ever generated by Mintro. | Criminal exposure; no exception exists for "testing" |
| A4 | No human in the loop between crawl and report. Borderline observations render as `not_evaluable` with the capture, never as a judgment. | Frank's ruling 2026-09-18; A1 |
| A5 | No post-boarding monitoring on Mintro's initiative. If IQWallet wants recurring checks it requests them in writing and receives the output. | 1.5 (fraud monitoring is IQWallet's) |
| A6 | Every merchant in this vertical is screened; every report reaches IQWallet before approval; delivery is retained with proof. | 1.4; indemnity 5.5 |
| A7 | No advisory content. The report never says what would make a finding go away. | July 2026 intermediary-advice ruling; 1.5 |
| A8 | Public surface only at screening time: no account creation, no purchase, no paid credits. Any merchant-supplied login is a separate, later decision under A5. | A3, A5 |

The existing hard constraints 1–9 still apply where they touch shared code.

## 2. What this vertical deliberately does not use

The peptide screener now has an angle-based evaluation layer: AI-drafted narrative, spectrum lean,
"Recommended placement" (domestic / international / referred out), operator editor, publish. That
layer is a Mintro assessment. It is tabled for the peptide vertical (Frank, 2026-09-18) and it is
**out of scope here by design**, not by omission:

- No angle set. No `EvaluationReport`. No placement. No operator note. No AI-drafted narrative.
- The adult vertical renders a findings report: observation, capture, source. That is the whole
  report.

This means the adult vertical needs a findings-report rendering path that is currently marked
superseded on the peptide side (D-262/263 labelled old checklist captures superseded and not
sendable). Discovery item 11.3 establishes whether that path is revivable per vertical or needs a
new component.

## 3. Segmentation and referral policy

Intake asks the merchant (or agent) to place the product in one or more categories. The crawl then
confirms or contradicts the answer by feature detection. A contradiction is itself a finding.

### 3.1 Categories

| # | Category | Defining feature | Referral policy |
|---|---|---|---|
| 1 | Text companion, fixed personas | Merchant-built characters, chat only | Refer |
| 2 | Text roleplay, user-created characters | Free-text character definition | Refer, attestation-heavy |
| 3 | Voice / call companion | Audio interaction | Refer, attestation-heavy |
| 4 | Image generation, curated library, no uploads | Prompt-only, no reference input | Refer |
| 5 | AI-creator marketplace | Third parties publish and sell generated sets | Refer, attestation-heavy |
| 6 | Open-prompt generation on unfiltered models | "No filter / uncensored / unrestricted" marketing; user-selectable NSFW models; LoRA loading | Do not refer |
| 7 | Reference-image upload, face swap, undress | Any upload control feeding generation; faceswap feature | Do not refer |
| 8 | Video generation | Any video output | Do not refer |
| 9 | Hybrid with real performers | 2257-bearing real-person content | Out of vertical |
| 10 | Model / LoRA / prompt marketplace | Sells the tooling | Do not refer |
| 11 | Minor-coded or animal-coded styling | Marketing terms, tags, category names | Do not refer |

"Do not refer" is Mintro's own marketing choice under 1.1. It is documented as **Mintro Referral
Policy — Adult AI, v1.0**, versioned like the rule set, and it says so in its own header. It is not
a standard, not a compliance criterion, and never quoted to a merchant as one.

### 3.1a Ratified v1.0 policy lines (Frank, 2026-09-18)

P-1. Mintro does not refer a merchant whose product accepts user-supplied images or video for
character creation or generation, by any means, for any purpose.

P-2. Mintro does not refer a merchant unless all of the following are observed or attested with
evidence: no minor-coded terms in the public catalogue or marketing; age constrained at character
creation; output-side moderation, CSAM hash-matching, and NCMEC reporting in place. (A refusal probe
becomes a fourth leg when the probe runner ships under D-289.)

Note: categories 6, 8, 10, 11 remain proposed, not yet ratified. Policy is versioned; each run stamps
the policy version it was screened under; earlier referrals are not re-judged when the policy
changes.

### 3.2 Detectors

Every "do not refer" category is defined by a machine-detectable feature or term so that intake
exclusion never depends on judgment:

- Upload control on any generation or character-creation surface (rendered DOM: `input[type=file]`,
  drag-drop zones, "upload reference", "use your photo").
- Faceswap / face-consistency feature language on product, docs, or pricing pages.
- Video product: "generate video", "animate", video pricing tier, `/video` routes.
- Model selection exposing NSFW or "uncensored" variants; LoRA / CivitAI references.
- Marketing lexicon: "no filter", "uncensored", "unrestricted", "no safe mode", "no limits".
- Minor-coded lexicon (whole-token, same matcher as NAME-002): teen, loli, shota, petite,
  schoolgirl, age-regression, and the merchant's own guideline term lists when published.
- Animal-coded explicit lexicon.
- Real-person lexicon in character libraries: celebrity names, "lookalike", "resembles".

If intake declares category 1 and the crawl detects an upload control, the run records
`segmentation_conflict` and the merchant is not referred. That is the only intake outcome besides
"proceeds to screen" and it is a policy application, not a finding about the merchant.

## 4. Pipeline

```
Intake ──► Surface crawl ──► Probe library ──► Attestations ──► Report ──► IQWallet
(3.x)      (public + docs)   (text-only)       (evidence)       (findings) (decides)
```

1. **Intake.** Segmentation form; referral policy applied; conflicts halt referral.
2. **Surface crawl.** Existing crawler. Adds: docs subdomain discovery (`docs.*`, `/docs`,
   `llms.txt`, `sitemap.xml` on the docs host) — merchants describe features to users far more
   candidly than to reviewers. Rendered DOM for client-rendered pages (create-character pages on
   the first candidate returned an empty body to fetch).
3. **Probe library.** New. Section 6.
4. **Attestations.** Existing mechanism, new question set. Section 8.
5. **Report.** Findings only. Section 9.
6. **Delivery.** Existing send path, to IQWallet, before approval, retained.

## 5. Rule set skeleton — `rules/ruleset-adult-ai.json`

Rule IDs carry a vertical prefix so shared tooling can tell them apart: `AIGATE-`, `AIPOL-`,
`AIFEAT-`, `AICAT-`, `AITD-`, `AIBILL-`, `AIMKT-`, `AIPRB-`, `AIATT-`. Each is one hyphen and a
letters-only prefix, as the rule ID pattern requires (`/^[A-Z]+-\d{3}$/`).

Engine states are unchanged (`fail`, `review`, `pass`, `not_evaluable`).

**Labels.** Each rule declares `sense: absent | present`. For `absent` rules a finding is the thing
being present; for `present` rules a finding is the thing being missing.

| Engine state | `sense: absent` | `sense: present` |
|---|---|---|
| `fail` | Observed | Not observed |
| `pass` | Not observed | Observed |
| `not_evaluable` | Could not be checked | Could not be checked |

Rule titles are phrased as the thing being looked for, so the label completes the sentence.
AITD-001..003, AIGATE-001..003, AIPOL-001..007 and AIBILL-001..003 are `present`; all others are
`absent`.

**Review.** The adult rule set declares every automated rule `auto_fail` and uses no co-occurrence
or value-collecting checks, so the review state never arises. Manual (AIATT-) rules resolve to
`not_evaluable` ('Could not be checked'); their attestation answers render in the attestations
section. Each AIATT- rule's params.reason names the attestation question that covers it.

The referral policy (section 3) is applied at intake; it is never rendered as a finding about the
merchant, and is rendered once in the report's boundary section as "Mintro's referral policy was
applied at intake."

### Source column

There is no published IQWallet standard for this vertical (Frank asked 2026-09-18; answer
expected "no" and will be retained). The report therefore does not carry a "Published standard"
column. It carries **Source**: the public rule or statute the observation relates to, quoted as a
short excerpt. Rules with no external source carry `source: mintro` and render under the existing
Mintro-observation heading (D-138 pattern).

`rules/sources/adult-ai-sources-v1.md` holds the excerpts (Mastercard Rules 5.12.7 text, AN 5196
requirements, TAKE IT DOWN removal window, SB 243 / NY Art. 47 disclosure language). The existing
byte-exact substring validator runs against it for every `source: programme` rule, with the same
vacuous-pass guards. Provenance header states each excerpt's origin document and date.

The source enum is unchanged; the rendered heading is vertical-aware copy ('Source' for this
vertical).

Mintro-authored text appears in exactly two places: rule titles, and the referral policy document.
Neither is a standard.

## 6. Probe library

Deferred to v1.1 under D-289. Not part of clusters 1–5.

### 6.1 Principle

Never request the prohibited artifact; request its precursor and record whether the system stops
there. A probe is a request that is legal to make; its acceptance is the finding.

### 6.2 Scope

- Text-only. Runs against the merchant's chat surface when one is reachable without an account or
  purchase (A8). If the chat surface is behind account creation, every probe rule is
  `not_evaluable` with reason `surface_not_public`, and that is reported as such.
- Probes behind account creation are `not_evaluable` unless the merchant supplies screening-time test
  access. That decision is shared with the peptide authenticated-crawl item.
- Graded from response text only: `refuse` (explicit refusal or policy statement),
  `comply` (the request is acted on), `silent` (no usable response). No image is ever requested.
- Fixed, versioned, committed as `rules/probes/adult-ai-probes-v1.json`. Counsel reviews the file
  before it runs. A probe not in the file is never sent. Version stamped on every run.

### 6.3 Probe classes (illustrative, not final text)

| Class | What it asks | What acceptance shows |
|---|---|---|
| Age policy | The character to state the platform's age policy for characters | Whether a policy is surfaced at all |
| Age token, non-sexual | A non-sexual scene with a minor-age token | Whether an adult-only platform rejects the age outright |
| Real person, non-explicit | A non-explicit scene with a named public figure | Whether real-person likeness is refused |
| Non-consent language, non-explicit | Non-explicit scenario using non-consent framing | Whether the framing is refused |
| Upload solicitation | Whether the character offers to use a photo the user provides | Whether upload-to-generate is offered in chat |

Final probe text is drafted separately, reviewed by counsel, and committed. The memo fixes the
classes and the grading, not the wording.

### 6.4 What probes cannot tell you

Whether a determined user can walk the model past guardrails over many turns. That is not
observable from outside and is not claimed. The report's boundary section says so.

## 7. Retention

- Probe transcripts: the request and the response text, retained with the run.
- No generated media is ever requested, so none is retained.
- Screenshots: existing capture path; adult pages are captured as any page is. Retention window
  and internal access are a policy question for Frank (section 14).

## 8. Attestations

Evidence-bearing where possible (document upload), free-text otherwise. Rendered as they are on
the peptide side: "Nothing in this section was observed or verified by Mintro."

1. Model provider and hosting: named third-party API vs self-hosted; model names.
2. Output-side moderation: classifier or review on generated output, not just prompt filtering;
   vendor named.
3. CSAM detection and reporting: hash-matching vendor; NCMEC reporting path.
4. Age assurance vendor and method for users.
5. Character creation constraints: how age is constrained; who moderates user-created characters.
6. Reference-image handling: whether uploads exist; if so, liveness / self-match verification.
7. Creator verification (category 5 only): identity and age of creators; pre-publication review.
8. Takedown SLA and complaint volume in last 12 months.
9. Mastercard registration status; VIRP tier; acquirer history.
10. App-store status and any removals.
11. Chargeback ratio, last 3 months.
12. State-law posture: which AV-law states are blocked or AV-gated; SB 243 protocols.

Unanswered renders as unanswered. No attestation is compared to a threshold.

## 9. Report and delivery

- Masthead: existing approved sentence, plus "Mintro reports what it observed; it does not
  underwrite the account or decide the outcome."
- Sections: what was observed (by category, each finding with capture and Source excerpt); what
  was attested; what was not checked (probe boundary, off-site presence, multi-turn behaviour);
  referral-policy line.
- No summary block. No counts in the email. No colours that encode good/bad.
- Recipient: IQWallet, before approval. Agent copy at Frank's discretion per existing send rules.
- Delivery record: existing send log, plus retention of the sent capture.
- Delivery evidence: the send log plus the CRM approval date. No approval event is built.

## 11. Read-only discovery for CC (before any build)

Items 11.1–11.7 are answered in `docs/discovery-adult-ai-vertical.md`. Item 11.8 is open.

1. **Vertical threading.** Where would a `vertical` key live: on the org, the merchant, or the run?
   Which of ruleset load, attestation set, report renderer, and send copy would need to branch on
   it. Report the minimal set of touch points.
2. **Rule set loader.** Whether `packages/ruleset` can load a second file and a second source
   corpus without changing the engine (hard constraint 1). What the validator assumes about file
   names.
3. **Findings report path.** Current state of the pre-evaluation checklist renderer and capture:
   dormant, deleted, or superseded-but-present. Whether it can render per vertical without
   reviving the peptide checklist send path.
4. **Crawler capabilities.** Whether the crawler can (a) discover and fetch a docs subdomain,
   (b) return rendered DOM for feature detection on client-rendered pages, (c) interact with a
   public chat widget (send text, read response) without creating an account. (c) decides whether
   probes are a crawler extension or a separate runner.
5. **Lexicon matcher.** Whether `textMatch.ts` / NAME-002 whole-token matching is reusable for the
   new lexicons as data, not code.
6. **Send and retention.** What the send log records; whether "delivered before approval" can be
   evidenced from existing data or needs a field.
7. **Copy audit (this vertical only).** Every rendered string that would be shared with the adult
   vertical containing fail / pass / blocker / clean / compliant / recommend.
8. **Manual rules and attestations.** 11.8 — Whether to link a manual rule to its attestation
   question so the rule row can render by answer status; today no link exists (schema.ts:216-221).
   Decide in cluster 4. *(Open.)*

Output: a discovery note in `docs/`, no code changes.

## 12. Order of work (clusters)

1. **Foundations.** Vertical key; rule set and source corpus files; validator extended; referral
   policy document committed; decision records.
2. **Intake and detectors.** Segmentation form; feature detectors; docs-host discovery; lexicons
   as data; segmentation-conflict handling.
3. **Probe runner (v1.1, deferred; gated on industry input rewritten to precursor form, counsel
   review, and the test-access decision).** Public chat surface interaction; grading; transcript
   retention; probe file versioning. See D-289.
4. **Attestations and report.** Question set; findings renderer with Source column; boundary
   section; capture.
5. **Delivery and process.** IQWallet send; delivery evidence; every-merchant rule in ops docs.
   Delivery evidence is the send log plus the CRM approval date; no approval event is built.
6. **First real screen.** xchar.ai, by hand against the rule set, as the accuracy audit — same
   method as the CoMo record, without its vocabulary. Runs without probes.

Each cluster: one held commit per stage, guards observed failing before trusted, deploy and review
before the next.
